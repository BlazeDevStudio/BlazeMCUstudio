# Inert UART framing lab — v0.4.13

**Status: real source code and target compilation fixture, not physical device validation.**

This increment supplies a bounded, native-testable C++ UART frame parser under `core/firmware/BlazeUartFrame.h` and two genuine Arduino sketches generated by `scripts/export-uart-lab.cjs`.

## Build / samples

Use an existing output parent directory:

```bash
node scripts/export-uart-lab.cjs /path/to/empty-output-root
```

This creates:

- `BlazeUartEsp32Initiator/BlazeUartEsp32Initiator.ino` for `esp32:esp32:esp32`, using `Serial1.begin(9600, SERIAL_8N1, 16, 17)` — GPIO16 RX, GPIO17 TX.
- `BlazeUartEsp8266Responder/BlazeUartEsp8266Responder.ino` for `esp8266:esp8266:generic`, using hardware UART0 `Serial.begin(9600)` — GPIO3 RX, GPIO1 TX.
- Each generated Arduino sketch directory includes an identical local copy of `BlazeUartFrame.h`.

The exporter fails rather than overwriting an existing lab sketch directory. It **does not** modify saved project source, existing workspace `pins`, a configured device's firmware, or automatically flash anything.

The source module declares a deterministic frame layout:

| Field | Bytes |
|---|---:|
| Start marker `0xA5` | 1 |
| Version `0x01` | 1 |
| Kind `0x01` PING or `0x02` PONG | 1 |
| Sequence (uint8, wraps) | 1 |
| Payload length (0–16) | 1 |
| Payload (arbitrary binary, including `0xA5`) | 0–16 |
| CRC-8 polynomial `0x07`, init `0x00` (over version through payload; no start marker) | 1 |

**Maximum 22 bytes**, fixed storage, no heap allocation by the framing module, 250 ms incomplete-frame timeout with unsigned `millis()` wrap. Invalid kinds, versions, lengths, and CRC are rejected. Only an inert PING generates an echo PONG with the same sequence and payload; PONG produces no reply. The ESP32 sample sends a PING at one-second intervals and counts matching one-byte PONG responses in a loop-local-module counter, with no GPIO outputs or serial debug text. The ESP8266 sample listens for and replies to PING. No security or authorization is implied by CRC or sequence numbers.

## CI verification contract

- Execute `tests/native/uart-frame-test.cpp` using genuine C++11 compilation and ASan/UBSan under Linux for known CRC vector, invalid packets, size bounds, payload including marker bytes, incomplete frames, `millis()` rollover, and fuzz/resynchronization cases.
- Generate and compile **both** Arduino sketch sources using pinned ESP8266 core 3.1.2 / ESP32 core 3.0.7 in the existing real-board compilation CI matrix. Preserve previous Blink, AVR and Windows portable app/GUI gates. Archive the compile logs.
- Node tests check safe exporter, exact local header copy, UART configurations, absence of GPIO control in frame codec and a no-overwrite refusal.

## NOT demonstrated / do not wire by inference

Real electrical wiring, GND continuity, actual connector breakout, TX-to-RX crossover, power regulation, UART USB converter/programming contention, level shifting, board variants and voltage/current are **unverified**. The ESP8266 UART0 may be shared with USB programming and debug hardware; while the classic ESP32 UART1 permits mapped RX16/TX17 in this example, carrier/PSRAM restrictions still require external review. Compilation does **not** prove UART transfer, frame latency, electrical safety, data integrity in noise, peer pairing, replay protection, authentication, encryption, or readiness for coin/relay control.

**No flashing, no payment or relay functions, no production signing or release.** The module must remain isolated from financial admission/control paths and is not automatically connected to the workspace planner. A future separate milestone can add user-controlled export of compatible project-specific pair sketches after pin and UART-peripheral ownership validation; real wire acceptance remains NO-GO until independent physical bench evidence.

## Saved workspace export — v0.4.14

The desktop **UART lab export…** action appears only when a saved workspace UART relationship has explicit signal selections. It calls a read-only source/target project recheck. Only one narrowly compiled topology is currently accepted:

- **Source:** classic ESP32 `esp32:esp32:esp32`, UART1 TX GPIO17, RX GPIO16 (project uses visual source ownership).
- **Target:** generic ESP8266 `esp8266:esp8266:generic`, UART0 TX GPIO1, RX GPIO3 (project uses visual source ownership).
- The projects must be separate, saved workspace members, and the existing firmware pin and peripheral collision tests must still pass. Any known voltage conflict, moved pin, unsupported board, manual source, or competing workspace GPIO claim blocks export.

The reviewed preview then displays **Choose folder and export lab sketches…**. A platform-native folder picker accepts a *parent directory*. The export rechecks everything after that picker before creating one new `BlazeUartLab-<link id prefix>` directory. It writes two independent `.ino` sketches from the exact same shared lab templates that CI compiles, with a local copy of the tested header in each folder, `manifest.json` tying the source and target workspace IDs and GPIO selections to the lab, and `READ_ME_FIRST.txt`. An existing output directory is never overwritten; partial temporary staging is cleaned. Project firmware files, stored workspace metadata, board configuration, physical hardware, payment/relay controls, and compile/flash processes are **not modified or invoked**.

**Important:** `eligible` / `status:review` means only that the software export's narrow preconditions are met. It does not mean safe electrical wiring, working UART traffic, provisioned security, validated harness layout, or permission to flash. No physical UART transfer has been witnessed. More board types and arbitrary pin mapping remain unsupported rather than borrowing unverified routing.

## Second curated board pairing — v0.4.15

The **classic ESP32 ↔ classic ESP32** pair is now independently compiled in the same UART lab workflow, without touching ordinary project code or permitting physical wiring. The exact reviewed saved configuration is:

| Endpoint | Arduino core target | Peripheral | Raw GPIO TX | Raw GPIO RX |
|---|---|---|---:|---:|
| Source | `esp32:esp32:esp32` | UART1 `Serial1` | 17 | 16 |
| Target | `esp32:esp32:esp32` | UART1 `Serial1` | 25 | 26 |

The existing **ESP32 UART1 → ESP8266 UART0** pair remains unchanged. Both pairing variants share the **identical C++ frame parser**, ESP32 PING initiator and inert `makePong` handler. A separate `BlazeUartEsp32Responder` implements UART1 PONG on RX26/TX25; only the ESP32-specific job builds this new source using pinned ESP32 Arduino core 3.0.7.

The desktop preview explicitly reports `dual-esp32-uart1` or `esp32-to-esp8266`. The exporter reopens the saved workspace project identities and checks existing graph/peripheral ownership and mutually-exclusive GPIO allocations immediately prior to writing. Wrong pin numbers are **rejected** rather than automatically substituted in the generated firmware. It writes either a separate ESP32/ESP32 pair or ESP32/ESP8266 pair, never both into an ambiguous folder.

**Native simulated link acceptance:** `tests/native/uart-pair-host-test.cpp` compiles the actual `BlazeUartFrame.h` and feeds two parser instances through a deterministic in-memory byte stream. It tests multiple cycles including sequence rollover, marker bytes within payloads, CRC-corrupted packets, dropped incomplete frames, timeout recovery, and refusal to reply to non-PING packets. This is **not a real COM-port, device-to-device, logic-analyzer, USB bridge or UART electrical test**.

Espressif's [ESP32-DevKitC documentation](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32/esp32-devkitc/user_guide.html) lists GPIO25/26 as header I/O and GPIO16/17 as available only on compatible module variants (e.g. WROOM rather than WROVER). Selecting the generic classic ESP32 Arduino FQBN does **not** establish which physical module is mounted or whether the carrier exposes or reserves those pins. Therefore both examples remain **development lab-only / not approved to wire or flash**. No payment, relay or actuator operations are permitted; CRC-8 is detection, not security.
